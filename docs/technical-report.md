## 1. 摘要

本项目是一个面向小学 1–4 年级孩子的**放学后时间规划本地网页原型**：孩子用自然语言说出今天要做什么，系统把话整理成结构化任务清单，经校对后自动排出包含学习分段、休息、晚饭、睡前洗漱的完整时间表，并带专注计时器与奖励机制。

本次工作聚焦三个问题，全部有实测支撑：

1. **识别速度慢**（用户主观感受）。定位到根因不是网络或模型能力，而是 **DeepSeek 思考模式默认开启**且 `reasoning_effort` 无法关闭它。关闭后端到端从 **5.8–6.5 s 降到 0.8–1.1 s（约 6 倍）**，长输入从 14.7 s 降到 2.0–2.3 s，输出 token 从 1558 降到 95。
2. **纯本地模型能否替代云端**。实测结论：**不能用来提速度**。本机 4B 模型质量达标但需 11–33 s/次，云端仅 1–2 s/次；本地化的真实价值只在隐私与离线，不在性能。
3. **排程该由谁做**。大模型只适合理解需求与抽取任务，**时间分配必须交给求解器**。自研零依赖 Node 求解器在 6 任务规模上以 **3 ms** 达到与 OR-Tools CP-SAT 相同的分配质量，且 CP-SAT 的"最优解"违反本项目两条硬约束（娱乐相邻、作业被切碎）。

同时新增了**语音输入**（浏览器原生 Web Speech API）与**本地模型可选接入**（llama.cpp + Vulkan），并留下完整的 JSON 契约、24 项求解器断言与 OR-Tools 对照基线。

| 关键指标              | 优化前            | 现状                       |
| ----------------- | -------------- | ------------------------ |
| 识别端到端（短输入 3 任务）   | 5.8–6.5 s      | **0.8–1.1 s**            |
| 识别端到端（长输入 10+ 任务） | 14.7 s         | **2.0–2.3 s**            |
| 输出 token / 单次     | 1558（思考占 1460） | **95（思考 0）**             |
| 排程求解（16 任务）       | 无求解器           | **12 ms**                |
| 外部依赖              | 0              | **0**（新功能同样零依赖）          |
| 自动化断言             | 0              | **42 项**（求解器 24 + 语音 18） |

## 2. 调研方法

本次所有结论均来自**在本机实际运行**，而非文档推断。主要手段：

| 手段           | 用途               | 产出实例                                                                       |
| ------------ | ---------------- | -------------------------------------------------------------------------- |
| 直接 HTTP 探测   | 验证路由、状态码、安全边界    | `/../server.mjs` → 404；`PUT /` → 405；无密钥 → 503                             |
| 供应商 API 直连剖析 | 区分"模型慢"与"我们的代码慢" | 发现 `thinking` 默认开启、`json_schema` 不被支持                                      |
| 独立 Node 脚本   | 复现页面逻辑并断言        | 抽取页面内联脚本 → 桩 DOM → 42 项断言                                                  |
| 子进程硬超时隔离     | 定位死循环            | 8 个用例逐一 spawn，8 s 超时定位到 `deadline` 用例                                      |
| 前后端同契约双跑     | 选型决策             | 同一份 JSON 输入分别喂给 Node 求解器与 CP-SAT                                           |
| 带宽实测         | 判断可行性            | GitHub 19 KB/s、hf-mirror 93 KB/s、ModelScope 5.5–6.3 MB/s、ghfast.top 1 MB/s |
| 官方文档核对       | 避免踩隐藏规则          | DeepSeek 要求 `json_object` 时提示词必须含 "json" 字样                                |

**一个方法论要点**：初测报告过"144 ms"这一异常值（因探针提示词极短），后续用完整提示词复测才发现真实量级在 1–4 s。**单次采样不足以定论，必须同条件复测并报告区间。**

### 3.2 关键设计决策

**决策一：前后端分离由 Node 服务端代理模型调用。**
不把 API 密钥放进网页。代价是需要启动本地服务；收益是密钥不外泄、可以在服务端做结构校验与纠错（这是"小模型乱填学科"能被兜住的前提）。**这一条直接决定了项目不能直接托管到 GitHub Pages**（详见 §8.2）。

**决策二：单文件前端 + 零依赖后端。**
`package.json` 只有脚本，无 `dependencies`。部署方式是"装 Node，`npm start`"。新增的求解器、语音输入、本地模型接入都保持了这个约束——求解器是自研而非引入 OR-Tools，语音用浏览器 API 而非引入 SDK。

**决策三：AI 与求解器职责分离。**
模型输出**任务清单**，求解器输出**时间表**。这条边界是整个项目的核心，见 §5。

### 3.3 数据流

```
孩子的话（键盘/语音）
   │
   ├─(可选) 浏览器内置规则解析 parseNaturalTasks ── 失败/接口不可用时兜底
   │
   ▼ POST /api/recognize-tasks { text }
server.mjs ──► 模型（云端或本地）
   │  · JSON Output / 语法约束解码
   │  · 归一化：subject 白名单、占位词清除、时长边界、source 裁剪
   │  · 排程线索：priority（必须/先做/作业加权）、deadline（"8点前"→"20:00"）、splittable
   ▼ 任务清单 → 校对表（用户可改）
   │
   ▼ POST /api/plan { request }
scheduler.mjs（纯计算，3–60 ms，零额度）
   │  · 7 种候选顺序 → 贪心布局 → 局部搜索 → 自检
   ▼ 时间表 blocks / unscheduled / metrics / validation
   │
   ▼ 时间轴渲染 + localStorage 持久化（仅本机）
```

## 4. AI 推理层

### 4.1 云端路径：一次 6 倍提速

**症状**：用户反馈识别慢。实测端到端 5.8–6.5 s（短输入）、14.7 s（长输入）。

**定位过程**：

1. 直连 API 对比 → 应用路径 5.8–6.5 s vs 直连 3.3–3.9 s，说明服务端开销可控，瓶颈在模型侧。
2. 查看 `usage.completion_tokens_details.reasoning_tokens` → **1558 个输出 token 里 1460 个是思维链**，真正有用的 JSON 只有约 120 个 token。
3. 调整 `reasoning_effort` 为 `low/high/max` 分别实测 → **2763 / 2662 / 4097 ms**，几乎没有区别，证明这个参数不是开关。
4. 查官方文档 → **思考模式默认开启**，正确开关是 OpenAI 格式下的 `thinking: { type: "disabled" }`。

**修复与效果**（`server.mjs`）：

| 场景          | 修复前                               | 修复后            |
| ----------- | --------------------------------- | -------------- |
| 短输入（3 任务）   | 5.8–6.5 s                         | **0.8–1.1 s**  |
| 长输入（10+ 任务） | 14.7 s                            | **2.0–2.3 s**  |
| 输出 token    | 1558（推理 1460）                     | **95（推理 0）**   |
| 长输入结果       | 曾出现 `finish=length` + 空 JSON（502） | 稳定返回 10–11 条任务 |

**附带修掉一个真实故障**：思考模式会吃满 `max_tokens` 导致 `content` 为空。这在长输入上是必现的，表现为前端弹"输入内容较多"——修复后消失。

实现上保留了开关：`DEEPSEEK_THINKING=enabled` 可恢复原行为。

**两条被文档验证的隐性规则**（此前只是"碰巧满足"）：

- DeepSeek **只支持 `response_format: {type:"json_object"}`，不支持 `json_schema`**。因此服务端必须自己校验结构（现状如此），不能依赖服务端语法约束。
- 使用 `json_object` 时，**提示词里必须出现 "json" 字样并提供格式示例**，否则返回 `400 invalid_request_error`。当前提示词末尾那句"请只返回符合以下结构的 JSON…"正好满足；**改动提示词时删掉这句就会全线 400**，已写进 README 警示。

### 4.2 本地路径：实测可用，但不该为速度而用

**动机**：孩子输入不离开本机 + 断网可用。用户曾希望同时提速，但实测否定了这一点。

**环境可行性**（先验证再动手）：

- Intel Arc 130T 通过 Vulkan 被 llama.cpp 识别，`KHR_coopmat` 矩阵核心可用、`uma: 1`（共享显存）。
- Windows Vulkan 预编译包：`llama-b11429-bin-win-vulkan-x64.zip`（31.8 MB），解压即用。
- 带宽：Hugging Face 直连超时；`hf-mirror.com` 93 KB/s；**ModelScope 5.5–6.3 MB/s**；GitHub 直连 19 KB/s，`ghfast.top` 代理约 1 MB/s。因此 **2.4 GB 模型 6 分钟下完，不需要 VPN**。

**推理性能**（llama-bench 实测）：

| 模型              | 量化     | 体积     | 预填充        | 生成         | 端到端识别   |
| --------------- | ------ | ------ | ---------- | ---------- | ------- |
| Qwen3-0.6B      | Q8_0   | 610 MB | 1972 tok/s | 52.7 tok/s | 9–15 s  |
| Qwen3-1.7B      | Q8_0   | 1.7 GB | 990 tok/s  | 23.1 tok/s | 9–14 s  |
| Qwen3-4B        | Q4_K_M | 2.4 GB | 357 tok/s  | 16.9 tok/s | 11–33 s |
| 同机 CPU（0.6B 对照） | Q8_0   | —      | 597 tok/s  | 38.0 tok/s | —       |

GPU 加速有效：0.6B 上预填充 3.3×、生成 1.4×。

**质量实测**（同一套 5 用例）：

| 模型           | 结论                                                                                           |
| ------------ | -------------------------------------------------------------------------------------------- |
| Qwen3-0.6B   | ❌ 不可用：学科被填成 `play`/`homework`，连写的 4 项英语作业合并成 1 条                                             |
| Qwen3-1.7B   | ⚠️ 不稳定：4 项英语作业能拆对，但给娱乐/休息任务乱填学科（Minecraft→音乐）                                                |
| **Qwen3-4B** | ✅ 达标：学科 11/11 全对，`复p23~24页 / 2背p26 / 3完成p23~29页 / 听读p28~30页` 全部拆对，时长按 15/15/20/25/25/30 正确分档 |

**过程中修掉的两个坑**：

1. **思维链吃光 token（本地版）**：Qwen3 默认先写思考。4B 实测 **70 s、1024 token 全用在思考上，JSON 为空**、接口报错。加载 `chat_template_kwargs: {enable_thinking: false}` 后降到 **12 s**。
2. **小模型照抄提示词里的例子**：我在提示词里写了范例 `"复p23-24页"`，结果模型**编出原话里根本没有的《夏洛的网》**、学科-来源还出现错位。改为"只讲规则、不给可抄的例子"后质量才达标。

**最终定位**：本地模型 = **隐私/离线选项**，不是性能选项。为速度就留在云端。

### 4.3 语音输入

用浏览器原生 `SpeechRecognition`（`zh-CN`，`continuous` + `interimResults`）：实时显示"听到：…"，定稿后**追加**进输入框而不自动提交，同一轮多句自动加逗号。

实测抓到一个真 bug：浏览器会**重复回传已定稿结果**，按 `resultIndex` 累加会产生 `"我要写语文作业我要写语文作业…"`。改为**每次事件从 0 重新拼接**（幂等）后修复。

**必须澄清的边界**：语音**不属于本地链路**——Chrome/Edge 的中文识别把**音频**送到浏览器厂商服务器，只有识别后的文字回到本机。要连音频也不出本机，需另起本地转写（whisper.cpp / faster-whisper / SenseVoice），本项目未实现，已在 README 说明。

## 5. 排程求解器（核心贡献）

### 5.1 问题定义

单孩子、单天、10–20 个任务的时间分配。输入是任务集合（时长、优先级、可否拆分、截止时间、固定时间、偏好时段）与排程窗口，输出是无重叠、满足硬约束的时间表。

**为什么不能交给大模型**：

| 能力                      | 大模型              | 求解器             |
| ----------------------- | ---------------- | --------------- |
| 听懂"英语4项作业复p23页…"并拆成任务   | ✅ 强              | ❌ 做不了           |
| 区分"看课外书=娱乐 / 读课文=学习"    | ✅ 强              | ❌ 做不了           |
| 16:00–21:00 内给出不重叠的时间表  | ⚠️ 会算错、会重叠或超时    | ✅ 保证            |
| 满足"8点前完成""18:30 钢琴课不能动" | ⚠️ 经常漏           | ✅ 硬约束可验证        |
| 每段学习 ≤20 分钟、娱乐不相邻       | ⚠️ 时好时坏          | ✅ 确定性           |
| 速度 / 费用                 | 1–2 s、按 token 计费 | **3–60 ms、零成本** |
| 可复现、可测试                 | ❌ 同输入结果漂移        | ✅ 纯函数           |

### 5.2 算法

1. **多起点贪心**：生成 7 种候选顺序（按截止时间 / 优先级 / 孩子优先 / 生活优先 / 休息优先 / 学娱交错 / 偏好优先），各自贪心布局，取评分最高者。
2. **局部搜索**：交换相邻两项 + 顺序轮换，接受更优解，直到 `budgetMs`（默认 400 ms）用尽。
3. **切分策略**：学习任务先算段数，**每段大小先定好，余数加到前几段**，保证每段 ≤ 专注上限且总量精确。
4. **可行性先行**：放置前先判断"最少时长是否还有可能放下"，不可能立即记为未排。

### 5.3 约束模型

硬约束（违反即 bug，`validation` 会报错）：块不重叠、全部落在窗口内、`fixed` 不被移动或占用、遵守 `window` 与 `deadline`、相邻娱乐之间必须有非娱乐块。

软约束（体现在 `objective`）：

```
objective = 2×作业分钟 + Σ(作业分钟 × (3 + priority×2)) + 1.5×娱乐分钟
          + 偏好命中分钟 − 8×未排分钟 − 1.5×娱乐缺口 − 3×偏好落空
          + 适度休息奖励（休息只按学习时长 20% 计分，上限 20 分钟，超出 4 倍扣分）
```

### 5.4 选型对比：自研 vs OR-Tools vs Timefold

同一份输入（6 个任务，含一个固定钢琴课）：

|         | OR-Tools CP-SAT（`tools/ortools_plan.py`）    | **自研 Node 求解器（采用）** |
| ------- | ------------------------------------------- | ------------------- |
| 状态      | OPTIMAL，12.9 ms                             | 校验通过，**3 ms**       |
| 作业 / 娱乐 | 60/60 分钟、60 分钟                              | 60/60 分钟、60 分钟      |
| 娱乐不相邻   | ❌ 两段娱乐贴在一起                                  | ✅ 中间插 5 分钟休息        |
| 最小段长    | ❌ 25 分钟作业被切成 15+10+**5** 碎片                 | ✅ 15+10，每段 ≥10      |
| 排布紧凑度   | 18:05–18:30 浪费 25 分钟                        | 更紧凑                 |
| 部署      | 需 Python + pip 包（本机有 `cp313` wheel，22.8 MB） | ✅ 零依赖               |

**关键发现：CP-SAT 的"最优解"违反本项目两条硬约束**——它需要额外建模才能表达"娱乐不相邻""最小段长"，而这两条在自研求解器里是原生的。Timefold / OptaPlanner 属 Java 生态（本机无 JDK），且 1.8k star 的 Timefold 与转入维护的 OptaPlanner 都不适合此规模。

**何时才值得换 CP-SAT**：任务上到几百个、跨天排程、需要最优性证明。JSON 契约已固定（[docs/schedule-contract.md](schedule-contract.md)），换的时候只改 `server.mjs` 中 `/api/plan` 的实现。

### 5.5 开发过程中修掉的 4 个真 bug

均来自测试暴露，非理论推演：

1. **死循环**：当 `deadline` 已过（`cursor` 越界）时，收缩逻辑永远无法把时长压到下限，原地打转。定位方式：子进程 8 s 硬超时 + 迭代计数器注入。修复：`place()` 改为"先判定可行性再放置"。
2. **目标函数在奖励休息**：求解器为多拿休息分，故意把作业切成"做 10 分钟休 5 分钟"（多切一段多 5 分钟休息）。修复：休息只按学习时长 20% 计分，超出 4 倍扣分。
3. **切分越界**：45 分钟作业 + 上限 20 → 切出 20 和 **25** 分钟（超上限），根因是"切到剩多少算多少"的取整方式。修复：先定段数、每段大小先定、余数给前几段。
4. **自动休息被计入任务时长**：`splitHomework` 生成的休息块带了 `sourceId`，导致 45 分钟作业在界面上显示成 55 分钟。修复：自动块 `sourceId = null` 并加 `countsTowardSource` 标记。

另有 2 处属于我自己的实现瑕疵（恒真条件、无效语句）与数处桩 DOM 不完整导致的误报，均在报告数据中剔除。

### 端到端实测样本

- 识别 **1618 ms** → 7 个任务；`口算两页` 自动标注 `priority=5`、`deadline=20:00`（由"8点前必须完成"正则抽取，非模型猜测）
- 排程 **7 ms**（求解器内部 3 ms，策略 `deadline`）→ 作业 105/105 分钟全排进、娱乐 60 分钟、`validation.ok=true`

- 填不下的任务**不静默丢弃**，带原因展示

## 8. 部署与发布

### 8.1 当前形态

本地服务 + 浏览器网页。`npm start`（云端）或 `node server.mjs --local`（本地模型）。

### 8.2 为什么不能直接托管到 GitHub Pages

GitHub Pages 只托管静态文件，**不会运行 `server.mjs`**：

|                | 本机                    | GitHub Pages       |
| -------------- | --------------------- | ------------------ |
| 谁调用模型 API      | Node 服务，密钥在服务端 `.env` | 只能浏览器直连            |
| **API 密钥**     | 网页里不可见                | **必须写进网页源码，公开可盗用** |
| 结构校验 / 纠错 / 裁剪 | 服务端有                  | 无                  |
| 谁的孩子在用         | 只有你                   | 全网任何人              |

**主要风险不是技术而是两条**：密钥会被白嫖；本项目本身引导填写孩子的作业与作息信息，公开托管等于邀请陌生人输入真实姓名、学校、住址。

**推荐**：GitHub 只当代码仓库，分享时让对方 `git clone` 后本机 `npm start`。若要联网版本，最小改造是"访客自填 Key + 隐私提示 + 输入限制"，或将服务端部署到能保密的平台（Vercel / Cloudflare Workers / 自有服务器）。

**仓库卫生现状（已核查）**：`.env` 未被跟踪且历史清白；`origin/main` 上 8 个文件均为源码；远端 `index.html` 无任何 `sk-` 形态密钥；`tools/llama/`、`tools/models/`（4.7 GB）已加入 `.gitignore`；本地与远端同为 `33e891a`（本次改动尚未推送）。

## 10. 未决问题

这些是**需要产品决策而非技术实现**的问题，我没有替你决定：

1. **优先级与截止时间是否要对家长可见可改？** 目前只在校对表内部生效，界面无控件。加两个控件即可，但会增加孩子的操作负担。
2. **纯娱乐场景要不要强插复习作业？** 当前为保证"娱乐不相邻"会插一段 10 分钟复习，与页面主张冲突。备选：改为插入休息，或允许两段娱乐相邻。
3. **是否要本地转写链路（语音也不出本机）？** 需要引入 whisper.cpp / faster-whisper 作为本地服务，会打破"零依赖"。
4. **数据导出与备份**：localStorage 清缓存即丢，是否需要导出 JSON / 导入？
5. **是否做输入停顿自动识别**（省掉一次点击）？实测当前整体已 1–2 s，收益有限；流式输出经测算只把首屏从 1.5–2.1 s 提前到 0.7–1.2 s，**判定不值得做**。
6. **`启动.command` 文件名与 Windows 启动脚本**：是否一并修复并提供跨平台启动方式。
